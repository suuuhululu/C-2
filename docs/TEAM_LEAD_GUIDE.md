## 일정 변경 판단

1. 변경 이유와 남은 실제 작업을 확인한다. 어려움을 숨기지 않고 일찍 요청한 사람에게 불이익을 주지 않는다.
2. 기능을 줄이거나 도와주면 기존 일정을 지킬 수 있는지 본다.
3. 선행·후행 Issue, 공용 장비 예약, 중간 점검·시연·발표 일정에 미치는 영향을 확인한다.
4. 수용하면 봇이 안내한 `/team approve-date 요청번호`로 승인한다. 수용할 수 없으면 `/team reject-date 요청번호 이유`로 반려하고 가능한 범위·지원 방안을 함께 정한다.
5. 영향을 받는 다른 Issue는 별도로 조정한다. 자동화가 전체 일정을 일괄 이동한다고 가정하지 않는다.

마일스톤을 바꾸면 후행 작업 마감이 자동으로 바뀌지 않는다. 공개된 강의 일정 변경은 강사 공지를 확인한 뒤 반영한다. 9/23 내부 통합 목표, 9/29 시연, 9/30 발표 준비는 [프로젝트 가이드](PROJECT_GUIDE.md)의 확인 범위를 따른다.

## 배정과 PR 관리

- 자동 배정의 열린 Issue 수는 작업 시간·난이도를 뜻하지 않는다. 자동 배정 2개, 실제 진행 1개를 기본으로 하되 시간 부족이면 새 작업을 만들기보다 범위를 줄인다.
- 역량·장비 접근·학습 목표가 맞지 않으면 Assignees를 수동으로 바꾸고 이유를 짧게 남긴다. 기존 담당자를 자동화가 덮어쓰지 않는다.
- 리뷰는 작성자 외 동료에게 분산한다. 리뷰 준비 시 PR에 검토자를 요청하고, 다음 수업일 안에 확인하도록 합의한다.
- CI 성공, 코드 검토, 실제 장비 검증을 따로 확인한다. 검증하지 않은 값을 보고서·PR에 넣지 않는다.
- 실기 검증 Issue는 구현 PR의 `Closes` 대상으로 넣지 않는다. 실제 결과와 기록을 확인한 뒤 닫는다.
- main 직접 push 차단·동료 승인 규칙을 유지한다. 초기화와 적용 절차는 [Git 가이드](GIT_GUIDE.md)를 따른다.

## AI를 사용하는 위치

팀장은 Issue 목표·현재 상태·제약을 AI에 주고 작업 분해, 빠진 완료 조건, 일정 충돌 후보, PR 변경 요약을 요청할 수 있다. 팀원도 관련 문서·로그·시도한 내용을 함께 주어 도움을 받는다. AI가 제안한 날짜·담당자·완료 판단은 확인 후 반영한다.

이 저장소의 배정·일정 처리는 정해진 규칙으로 동작하며 별도 AI API를 호출하지 않는다. 문장만 보고 AI가 마감을 바꾸거나 팀원을 평가하는 구성은 아니다. AI 자동 PR 리뷰를 설정한 기록은 없으며 현재 연결 상태는 별도 확인이 필요하다.

## 시스템 상태 확인

첫 적용 주에는 Actions 실패 여부와 날짜 승인 결과를 매일 확인한다. 정상 동작이 확인되면 변경 요청·지연·실패만 우선 본다. 매주 또는 역할 변경 시 설정의 active·roles·배정 한도와 실제 가용 시간을 맞춘다.

GitHub 알림을 팀원 모두가 받는지 연습에서 확인한다. 알림이 오지 않는 경우 Issue 구독과 계정 알림 설정을 확인하고, 매일 수업 후 자기 Issue 목록을 확인하는 습관을 함께 둔다.
