## 팀 운영

팀은 이수현(팀장), 김세은, 노홍동, 이시율 4명으로 확인했다. 담당 분야는 아직 미정이며 초기 Issue는 general 분야에서 작업량을 기준으로 배정한다. 공정·ROS 통합, 로봇 동작, 그리퍼·공작물, HMI·시험 영역을 참고해 이후 담당자와 동료 검토자를 정한다. 일정 담당자도 구현에 참여하고, 각 담당자가 자기 기능의 문서·시험 결과를 작성한다. 운영 절차는 [팀장 가이드](TEAM_LEAD_GUIDE.md)와 [팀원 시작 가이드](TEAM_ONBOARDING.md)를 따른다.

- 작업은 30~90분 안에 결과를 남길 크기로 나눈다.
- 한 사람의 진행 중 핵심 작업은 1개를 기본으로 한다.
- 매일 10분 공유: 완료 증거 → 막힌 점 → 다음 행동.
- 30분 정도 진전이 없으면 증상·로그·시도 내용을 정리해 동료나 강사에게 질문한다.
- 리뷰 요청은 다음 수업일 안에 응답한다. 모든 리뷰를 팀장에게 몰지 않는다.
- 장비 예약에는 목적·시간·실행자·필요 조건·남길 증거를 적는다.
- 기여도는 커밋 수보다 완료 작업·교차 검토·문제 해결·실험 기록으로 확인한다.

## 작업 상태와 평가 증거

현재 개발 일정은 GitHub Issue의 확정 마감 댓글·상태 라벨로 관리한다. 학습·발표 자료는 기존 Notion 자료와 링크로 연결하고, 공통 기술 결정과 재현 방법은 저장소 Markdown에 남긴다.

상태는 `할 일 → 진행 중 → 검토 중 → 완료`, 별도 `막힘`으로 운영한다. 현재 실행 중인 [Issue 자동화](ISSUE_AUTOMATION.md)는 status 라벨을 관리하며 Projects·외부 캘린더 동기화는 제공하지 않는다. 구현과 실기 검증은 다른 Issue로 관리한다. PR 병합은 실기 성공을 의미하지 않는다.

| 평가 관점 | 남길 증거 |
| --- | --- |
| 기능 완전성 | 요구 기능 ↔ Issue ↔ PR ↔ 시험 결과 |
| 정확성·안정성 | 동일 조건의 실제 반복 결과·실패 조건 |
| 입출력 이해 | 모듈 연결표·단위·완료 판단 |
| 오류 대응 | 제한 시간·후속 공정 차단·상태 확인 후 복구 절차 |
| 개인 협업 | 담당 작업·검토·의사결정·피드백 반영 |

코드·문서·영상에는 시험한 커밋을 기록한다. 재현 가능한 시연 버전은 실제 검증 후 태그를 부여한다. 아직 수행하지 않은 성공률·시간·시연 결과는 작성하지 않는다.
